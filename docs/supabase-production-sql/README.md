# Подготовка Supabase Production — до выполнения требуется отдельное подтверждение

1. В Supabase проверьте ID проекта `ixkgemsihkuuzquyolbt`, имя и регион. Проверьте другие пользовательские схемы, таблицы, представления и роли. Скрипт проверяет посторонние объекты только в `public`; он не удостоверяет ID проекта. Не выполняйте при сомнениях.
2. После подтверждения выполните `01_schema_production.sql` целиком в одной транзакции. Если в public есть посторонние объекты или таблицы приложения без маркера production, операция остановится. При уже существующих таблицах `IF NOT EXISTS` не сверяет их состав — сначала выполните проверку структуры и остановитесь при расхождениях. Скрипт не удаляет существующие политики или постолбцовые права.
3. Выполните `02_catalog_production.sql`, затем запросы из `03_verify_production.sql` по отдельности. Проверьте отсутствие строк с problem, валидность индексов, RLS, права ролей на таблицы, столбцы и последовательности, существующие политики и Security Advisor. Маркер должен быть `(1, production)`, каталог должен содержать ровно 12 записей без расхождений. До создания аккаунтов все пять счётчиков пользовательских данных должны быть нулевыми.
4. Повторный запуск схемы и каталога не удаляет данные и не перезаписывает существующие ID. При частичном выполнении, ошибке или несовпадении структуры/каталога остановитесь и разберите состояние; не удаляйте таблицы и не меняйте маркер другого окружения. Проверочный SQL только читает данные.
5. Аккаунты создавайте отдельно для Production из безопасной административной среды, где работает PostgreSQL-соединение. Задайте `APP_ENV=production`, `DB_SSL_MODE=require`, Production Transaction pooler как `DATABASE_URL`, затем используйте `python -m app.setup create-user --username anna --name Анна --role client`, аналогично `maxim` и `admin` (`--role admin`). Команда дважды запрашивает каждый отдельный пароль скрыто, применяет scrypt приложения и не перезаписывает занятый логин. В PowerShell строку подключения вводите через `Read-Host -AsSecureString`; не отправляйте пароли или хеши в чат или SQL-файлы. Проверку пароля выполняйте локально через `app.security.verify_password` без вывода хеша. Если соединение обрывается, остановитесь и проверьте существование аккаунта до повтора.
6. Только после подтверждения и подготовки базы создайте отдельный Render Web Service из `main` после согласованного PR с инфраструктурой. Python 3.12; build `pip install -r requirements.txt`; start `uvicorn index:app --host 0.0.0.0 --port $PORT`. Задайте `APP_ENV=production`, `COOKIE_SECURE=true`, `DB_SSL_MODE=require`, `PUBLIC_ORIGIN` фактического HTTPS-домена, Production `DATABASE_URL` и `ROUTERAI_API_KEY` в защищённых настройках Render. Не используйте значения Preview. Маркер базы проверяется при запуске FastAPI; локальное соединение с pooler ранее прерывалось, работу из Render нужно проверить отдельно.

SQL не создаёт пользователей, не содержит паролей и не переносит историю. Роль приложения должна иметь нужные права на таблицы/последовательности и обходить RLS как владелец либо иметь отдельные ограниченные политики; привилегии не передаются браузеру. Проверьте права и политики перед запуском.

Проверочный скрипт выполняется целиком и выводит в сообщениях NOTICE один итог PASS или FAIL с причинами. Отсутствие обязательных таблиц — FAIL; при ошибке структуры проверка данных пропускается. Перед выполнением в Production необходимо испытать скрипты на отдельной PostgreSQL-базе: эта версия ещё не прошла такое испытание. Повторный запуск схемы может вновь включить RLS и отозвать права, но не должен менять строки; каталог добавляет отсутствующие ID и не исправляет существующие. Проверьте итог после повторения и не запускайте скрипты при несовпадениях.
