# Подготовка и выпуск учебного стенда

Этот документ описывает ручную настройку. Скрипты проекта не создают GitHub-репозитории, проекты Supabase или Render и не публикуют приложение.

## Окружения и данные

Используйте две отдельные базы Supabase: одну для production, другую для preview. Локальная разработка по умолчанию использует `data/apartments.db`; тесты — временные базы. Подключать обычные тесты к рабочей или preview-базе нельзя. `APP_ENV` принимает `development`, `test`, `preview`, `production`. На Render окружение задаётся явно через `APP_ENV`; маркер базы должен совпадать.

У команды `init` есть маркер окружения в базе: уже инициализированную production-базу нельзя использовать для preview и наоборот. При наличии таблиц приложения без маркера облачная инициализация останавливается; перенос старой базы требует отдельного плана и проверки. Не направляйте `reset_demo.py` на облачную базу: скрипт ограничен локальной SQLite.

`create_all` создаёт отсутствующие таблицы, но не мигрирует существующие колонки и индексы. Перед последующими изменениями схемы нужны отдельные миграции и резервная копия. Для перехода существующих пользователей и истории из SQLite потребуется отдельный проверенный перенос; он не выполняется автоматически.

## Supabase

1. Создайте отдельные проекты/базы для production и preview. Получите строку подключения PostgreSQL **Transaction pooler** из панели Connect. Потребуются адрес, порт, имя базы, имя пользователя и пароль. Пароль не помещайте в Git и не передавайте в чат.
2. Сохраните URL каждого окружения отдельно как `DATABASE_URL`. SQLAlchemy использует драйвер psycopg, `NullPool`, отключённые prepared statements и `DB_SSL_MODE=require` по умолчанию. Для проверки сертификата задайте `DB_SSL_MODE=verify-full` и настройте корневой сертификат для libpq; режим `disable` разрешён только в development/test. Инструкция Supabase: https://supabase.com/kb/troubleshooting/using-sqlalchemy-with-supabase-FUqebT
3. В безопасной административной среде с переменными именно нужного окружения выполните `python -m app.setup init` и затем `python -m app.setup create-user --username ... --name ... --role client` или `--role admin`. Пароли вводятся скрыто. Повторный `init` не меняет учётные записи и не удаляет данные.
4. Настройте минимально необходимые права роли PostgreSQL. Самодельная авторизация приложения продолжает проверять права на сервере; нельзя считать RLS автоматически настроенной защитой при прямом SQL-подключении.

В PowerShell можно ввести строку подключения скрыто, не записывая её в историю команды:

```powershell
$apartmentDbSecret = Read-Host 'DATABASE_URL нужного окружения' -AsSecureString
$env:DATABASE_URL = [System.Net.NetworkCredential]::new('', $apartmentDbSecret).Password
$env:APP_ENV = 'preview' # отдельно повторить для production с другой базой
.\.venv\Scripts\python.exe -m app.setup init
.\.venv\Scripts\python.exe -m app.setup create-user --username demo --name Клиент --role client
Remove-Item Env:DATABASE_URL
```

Команда init не изменяет существующие пароли или роли. Используйте уникальные демонстрационные учётные данные для каждого окружения.

## Render

Создайте отдельный Web Service для preview из ветки `deploy/preview-validation`. Production в будущем создаётся отдельным Web Service из `main` со своей production-базой и отдельными переменными. Не копируйте URL Preview в Production.

Runtime: Python; Build Command: `pip install -r requirements.txt`; Start Command: `uvicorn index:app --host 0.0.0.0 --port $PORT`. Файл `.python-version` задаёт Python 3.12, как в GitHub Actions. `render.yaml` описывает только Preview; для обычного ручного Web Service те же параметры задаются в форме.

В настройках Preview задайте `APP_ENV=preview`, `DB_SSL_MODE=require`, `COOKIE_SECURE=true`, `PUBLIC_ORIGIN=https://<точное-имя-сервиса>.onrender.com`, `DATABASE_URL` существующего Supabase Preview Transaction pooler и `ROUTERAI_API_KEY`. Последние два значения вводите только в защищённые настройки сервиса. `PUBLIC_ORIGIN` должен точно совпадать с адресом в браузере, без завершающего слеша; для другого домена его надо отдельно настроить. Не помещайте секреты в Git и журналы.

База Preview уже подготовлена: повторная инициализация ей не нужна. Проверьте сборку и логи, открытие страницы и CSS/JS, каталог, вход/выход, cookies, CSRF, изоляцию пользователей и сохранение фактов и диалогов после перезапуска. Сначала убедитесь, что в интерфейсе Render задан точный домен для `PUBLIC_ORIGIN`; после его изменения нужен новый деплой.

Free Web Service останавливается после 15 минут без входящих запросов и при следующем запросе запускается около минуты; локальная файловая система временная. Бесплатные часы ограничены, после исчерпания бесплатные сервисы приостанавливаются. Данные приложения должны оставаться в Supabase, не в локальной SQLite. Условия: https://render.com/docs/free

## GitHub Actions

При push и pull request workflow устанавливает зависимости, проверяет синтаксис, импорт и ресурсы, поднимает отдельный PostgreSQL-сервис и запускает весь pytest. Реальные секреты и рабочие базы для CI не нужны. Первый запуск Actions станет возможен только после создания и подключения репозитория. Перед первым коммитом проверьте будущий набор файлов и историю на секреты; `.env`, данные, логи и диагностические материалы исключены правилами `.gitignore` и `.vercelignore`.

## Ограничения

Лимиты и блокировки пользователей лежат в PostgreSQL и работают между процессами, но фиксированные интервалы, глобальная квота и блокировка на 10 минут — упрощение для учебного стенда. Глобальная квота может временно заблокировать всех пользователей при атаке. Для реальной публичной эксплуатации потребуются дополнительные ограничения на внешнем периметре, мониторинг, надёжная политика аутентификации и оценка правил хранения данных. Секреты хранятся в настройках окружений, а не в репозитории.
